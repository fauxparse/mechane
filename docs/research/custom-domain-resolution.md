# Resolving a Custom Domain to its Device, and the CORS that admits it

Research for [#816](https://github.com/fauxparse/mechane/issues/816), part of [Custom Domains for the Player](https://github.com/fauxparse/mechane/issues/814).
Date: 2026-09-28. Code claims cite this repo at `main`@`c8a5e351`; external claims cite primary sources (WHATWG Fetch Standard, Vercel docs, Better Auth docs, TanStack Router docs), all accessed 2026-09-28. Anything unverified is marked **[unverified]**.

## The question

When the Player SPA loads on a Custom Domain, how does it learn which Device to open, and what CORS policy lets it call the API from an arbitrary origin? Compare client-side host lookup, edge rewrite/middleware, and an API-issued redirect on: first-paint latency on cellular, pairing-code exposure in the URL bar, mapping cache/rebind/revocation timing, and behaviour for unbound hosts. Then settle the CORS policy for public Player operations (`playerSession`, `submitPlayerEvent`, `/api/realtime/auth`) and confirm whether Better Auth `trustedOrigins` must change.

## Headline recommendation

**Client-side resolution: the Player calls a small public REST endpoint with `location.host` and receives the pairing code; CORS becomes split-horizon — first-party origins keep today's credentialed exact-origin allowlist, every other origin gets non-credentialed `Access-Control-Allow-Origin: *` — and Better Auth `trustedOrigins` does not change.**

The Player already has everything but the code: `usePlayerSession(code)` drives the whole Device experience from a pairing code (`apps/player/src/api.ts`). Resolution is the act of turning `location.host` into that code. Doing it client-side needs no edge compute and no second data store, works on any ingress that can serve the SPA over TLS, keeps the URL bar clean, and makes the unbound-host case a client-rendered holding page. The cost is one extra cross-origin round trip on first load (a plain GET, no preflight, HTTP-cacheable), which is the right trade until measured otherwise. The CORS finding is independent of that choice and of the ingress: because `packages/graphql-schema/src/client.ts` hardcodes `credentials: "include"`, no wildcard policy can ever serve a custom-domain Player — the Player must stop sending credentials it does not need, after which any-origin non-credentialed CORS is safe for the public Player operations and _safer_ than a dynamic credentialed allowlist.

## What the Player does today (code facts)

- Routes: `/` (pairing-code splash, `apps/player/src/routes/index.tsx`) and `/s/$code` (`apps/player/src/routes/s/$code.tsx` → `PlayerView`); the root route is a bare `Outlet`. `apps/player/vercel.json` rewrites `/(.*)` to `/index.html` — a pure static SPA, no server code on the Player project.
- The API base is fixed and cross-origin from every Player host: `defaultApiBaseUrl` returns `https://api.mechane.dev` in production (`apps/player/src/api-url.ts`), regardless of which host served the SPA. A Player on a Custom Domain therefore always calls the API cross-origin; CORS is unavoidable for every resolution option (a same-origin `/api` proxy on the Custom Domain is rejected below).
- Auth is the Bearer pairing code, never a cookie: `fetchPlayerSession`/`submitPlayerEvent` send `Authorization: Bearer <code>` (`apps/player/src/api.ts`); `createContext` extracts it via `bearerCredential` while cookies resolve the _Studio_ identity (`apps/api/src/graphql/context.ts`); `playerSession` returns `null` without a valid credential and `submitPlayerEvent` requires it (`apps/api/src/graphql/player-session.ts`) — the credential is the authorization.
- Transport: `graphqlRequest` always sends `credentials: "include"` (`packages/graphql-schema/src/client.ts`), shared with Studio (which needs the cookie). `/api/realtime/auth` is fetched with a bare `fetch(url)` (`packages/realtime/src/browser.ts:141`) — per the Fetch Standard the default credentials mode is `same-origin` ([Fetch §5.2 `RequestInit`](https://fetch.spec.whatwg.org/#dom-requestinit-credentials)), so this call is **already non-credentialed** cross-origin.
- CORS is one exact-origin allowlist used everywhere: `applyCorsHeaders` echoes the origin plus `Access-Control-Allow-Credentials: true`, `Vary: Origin`, methods, and `Content-Type, Authorization` headers, only when `ALLOWED_ORIGINS` contains it (`apps/api/src/lib/cors.ts`); graphql-yoga mirrors it (`cors: { origin: ALLOWED_ORIGINS, credentials: true }`, `apps/api/src/graphql/server.ts`); `/api/realtime/auth` applies the same gate (`apps/api/src/realtime-auth.ts`). Better Auth's `trustedOrigins` **is** `ALLOWED_ORIGINS` (`apps/api/src/auth.ts`) — the API's `/api/auth/*` routes and CORS share one list.
- Nothing resolves a tenant from `Host`: `httpHandler` dispatches by path only (`apps/api/src/http-handler.ts`).

## A fact that reshapes the option set: rewrites are invisible to this SPA

A server-side rewrite changes which _resource_ serves the request, not the browser's URL. TanStack Router routes on the browser URL via `createBrowserHistory` (the default history) ([TanStack Router, History types](https://tanstack.com/router/latest/docs/framework/react/guide/history-types)); the SPA is served as `index.html` for all paths only so client-side routing survives deep links ([TanStack Router, Deploy to production](https://tanstack.com/router/latest/docs/how-to/deploy-to-production)). So middleware rewriting `/` → `/s/ABC12` serves the same `index.html` to a browser still showing `https://vote.knifefight.nz/` — the router boots the splash route, and the code never reaches the client. An edge component that wants to hand the code to a client-rendered SPA must either:

- **redirect** to `/s/<code>` (the URL changes; the code lands in the URL bar), or
- **set a host-only cookie** (readable via `document.cookie` at boot) while rewriting/continuing, or
- not bother, and let the client resolve (Option A).

Response headers on the HTML document are not readable from JS, and static assets cannot be modified in flight, so those are the only shapes. This is why "edge rewrite mapping host to `/s/<code>`" as posed collapses into redirect-or-cookie.

### Option A — client-side lookup by `location.host`

The SPA on any non-first-party host calls `GET <API>/api/player-domains/resolve?host=vote.knifefight.nz` before or while loading, gets `{ pairingCode }`, and feeds the existing `usePlayerSession`. On 404 it renders the holding page. Details:

- **Latency.** The resolve call is a CORS-safelisted GET (no `Authorization`, no JSON content type), so it is a _simple request_ — no preflight OPTIONS round trip ([Fetch §3.3.2 HTTP requests](https://fetch.spec.whatwg.org/#http-requests)); the GraphQL session call that follows is a POST with `Content-Type: application/json` + `Authorization` and does preflight (cached by the browser thereafter). One extra RTT (~50–300 ms on cellular) on a cold first visit; `Cache-Control: public, max-age=300`-style caching on the resolve response removes it for repeat visits within the TTL, at the cost of a rebind/revocation lag bounded by that TTL. If that trade ever bites, the endpoint's TTL is a knob, not an architecture change.
- **Code exposure.** None in the URL. The code lives in memory only — strictly better than today's `/s/<code>` links for shoulder-surfing/screenshots of a vanity URL, though see below: the code is already a public artifact, so this is polish, not security.
- **Unbound hosts.** Client-side holding page; no edge logic; the ingress merely serves the SPA (TLS for bound-but-pending hosts is the ingress ticket's concern, and the standing decision already says an uncertificated host is not servable).

### Option B — edge middleware on the ingress

Vercel's current docs generalize the old Next-only "Edge Middleware" into **Routing Middleware**: "You can use Routing Middleware with **any framework**", configured via `vercel.json`'s `proxy` entrypoint (Node.js runtime) or a root `middleware.ts` (Edge runtime default), running "globally before the cache" ([Vercel, Routing Middleware](https://vercel.com/docs/routing-middleware); [API](https://vercel.com/docs/routing-middleware/api)). Static `vercel.json` redirects/rewrites with `has: [{ "type": "host", "value": … }]` conditions exist ([Vercel KB, subdomain→subpath](https://vercel.com/kb/guide/can-i-redirect-from-a-subdomain-to-a-subpath)) but are evaluated at build time and capped at 2,048 entries ([Vercel, Configuration redirects](https://vercel.com/docs/routing/redirects/configuration-redirects)) — user-added, runtime-mutable bindings cannot live there. So Option B means middleware reading the host and consulting either:

- **Vercel Global Config** (formerly Edge Config): "reads … within 15ms at P99, or often less than 1ms", "updates propagate globally with no redeployment required" ([Vercel, Global Config](https://vercel.com/docs/global-config)) — the fast path, but a second copy of the binding data with its own write path and failure modes; or
- **the API's resolve endpoint** (Option A's endpoint, reused) — one edge→API hop (~50–150 ms) added to HTML delivery unless response caching is layered on.

Then it must redirect to `/s/<code>` (URL-bar exposure, one RTT) or set a cookie the SPA reads (cleanest UX; the SPA needs the same "read a cookie instead of a path param" branch it needs for Option A anyway). **Ingress dependency:** if the ingress is the Vercel Player project with domains attached, this is available today; if it is a pure static host or a TLS-terminating proxy without compute, it is not. If it is a different edge (e.g. a Workers-based ingress), the analysis transfers but the store becomes that edge's KV.

### Option C — API-issued redirect

Something in front of the SPA (middleware again, or a proxy) asks the API where this host should go and returns a 30x. Redirecting to the first-party `show.mechane.dev/s/<code>` defeats the feature (the audience visibly leaves the branded domain the QR code pointed at); redirecting to `/s/<code>` on the same host costs a serial RTT before the first byte of HTML and puts the code in the URL bar. Every dependency of Option B applies, plus the redirect. It is dominated by both alternatives; the only argument ever raised for it — "the API is the single decision point" — is equally true of Option A's resolve endpoint without the redirect.

### Rejected aside: same-origin `/api` proxy on the Custom Domain

Vercel rewrites can proxy to an external deployment ([Vercel KB, reverse proxy](https://vercel.com/kb/guide/vercel-reverse-proxy-rewrites-external)), which would dissolve the CORS question entirely. It is rejected here: it would scope Better Auth's session cookies onto the user's domain and expose `/api/auth/*` there, dragging in exactly the cookie/`trustedOrigins` work the map rules out of scope for Player-only Custom Domains.

## Does the pairing code in the URL bar matter?

Not materially. The code is the product's existing public share artifact: Studio prints `PLAYER_BASE_URL + /s/<code>` links and QR codes (`apps/studio/src/api/client.ts` `playerSessionUrl`), it is 5 characters from a 30-character unambiguous alphabet (`packages/domain/src/pairing-code.ts`), it is Show-level and survives Runs, and the standing decisions keep `/s/<code>` working forever. Anyone who can screenshot a Custom Domain can photograph a poster. The real differences are cosmetic (a clean vanity URL shares better) and hygiene (browser history on the user's own domain stays code-free). The "opaque session credential" variant — resolve returns a bearer token that is not the pairing code — buys nothing while `/s/<code>` remains valid (the code stays a working credential regardless), and costs a second credential type threaded through `createContext`, `requirePlayerPairingCode`, and the realtime-grant flow. Recommend the plain pairing code.

## CORS: what `credentials: "include"` forces, and the policy that follows

### The spec mechanics

- Credentials modes are `omit` / `same-origin` / `include`; `include` sends cookies cross-origin ([Fetch §5.2](https://fetch.spec.whatwg.org/#dom-requestinit-credentials)).
- **`Access-Control-Allow-Origin: *` never works for a credentialed request.** The CORS check succeeds on `*` only "if request's credentials mode is not `include`"; an `include` request needs a byte-exact origin echo _and_ `Access-Control-Allow-Credentials: true` ([Fetch §4.10 CORS check](https://fetch.spec.whatwg.org/#cors-check); table of legal/illegal combinations in [§3.3.3 HTTP responses](https://fetch.spec.whatwg.org/#http-responses)). This is exactly why today's wildcard-free allowlist exists — `apps/api/src/graphql/server.ts` already carries that comment.
- **This also holds at preflight.** The preflight response's CORS check "is done on _request_ rather than _preflight_ to ensure the correct credentials mode is used" ([Fetch §4.8 step 7](https://fetch.spec.whatwg.org/#cors-preflight-fetch-0)) — so a credentialed request whose preflight answers `*` fails _before the actual request is sent_. A GraphQL POST (JSON content type + `Authorization`) is always preflighted, so an any-origin `*` policy does **not** let a third-party page fire cookie-authenticated mutations: the preflight rejects the credentialed request outright, and un-preflightable "simple" cross-site POSTs (`text/plain`) cannot carry the Better Auth cookie anyway because it is `SameSite=Lax` by default ([Better Auth, Security — CSRF protection & cookies](https://better-auth.com/docs/reference/security)).
- `Access-Control-Allow-Headers: *` would not cover `Authorization` (it is a "CORS non-wildcard request-header name", [Fetch §4.9 cache matching](https://fetch.spec.whatwg.org/#cors-preflight-cache)) — keep the explicit `Content-Type, Authorization` list `cors.ts` already sends.
- Responses whose CORS headers vary by origin must carry `Vary: Origin` ([Fetch §3.3, `Vary` guidance](https://fetch.spec.whatwg.org/#example-vary-origin)); `cors.ts` already does.

### The policy: split-horizon, not a dynamic allowlist

`/api/graphql` is a shared endpoint: Studio authenticates by cookie (needs `include`), the Player by Bearer code (needs nothing). So the origin decision is per-`Origin`, not per-endpoint:

1. **`Origin` on the first-party allowlist** (Studio, first-party Player, Site — exactly today's `ALLOWED_ORIGINS`): echo it with `Access-Control-Allow-Credentials: true`. Unchanged behaviour for Studio and Site.
2. **Any other origin**: `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`, **no** `Access-Control-Allow-Credentials`. No DB lookup, no verification coupling, nothing to revoke.

With that, the Player must call with `credentials: "omit"` (it never needed cookies): `*` then satisfies the CORS check for it, on the GraphQL endpoint and on `/api/realtime/auth` — the realtime fetch already omits credentials by default, so it works with **zero** client change. `submitPlayerEvent` from a custom domain is then admitted like any origin's non-credentialed request; that is safe because authorization _is_ the Bearer pairing code (`player-session.ts`), and an attacker with the code already has everything CORS could withhold — the same posture as today's `/s/<code>` on the first-party host.

**Why not a dynamic allowlist of verified Custom Domains?** It is strictly worse: it would grant _credentialed_ trust (readable responses) to origins any user can mint by verifying a domain they control — every Mechanē user could then read cookie-authenticated API responses for every visitor their domain attracts. Because `trustedOrigins: ALLOWED_ORIGINS` (`apps/api/src/auth.ts`), feeding verified domains into the same list would additionally make `/api/auth/*` (sign-in, OAuth callbacks) trust user-controlled origins — Better Auth uses `trustedOrigins` precisely to reject untrusted origins on those routes ([Better Auth, Security](https://better-auth.com/docs/reference/security)). It also couples the CORS path to the binding-verification lifecycle and adds a per-request lookup where none is needed. The split policy gives custom-domain Players everything they need while keeping credentialed trust first-party-only — a smaller trusted surface than today's, not a larger one.

**`trustedOrigins` therefore does not change.** The Player never touches `/api/auth/*` (its only API calls are the GraphQL endpoint and `/api/realtime/auth`, per `apps/player/src/api.ts` and `packages/realtime/src/browser.ts`), and origin checks on those routes are Better Auth's concern only for cookie flows. Custom Domain origins must deliberately _not_ be added to `ALLOWED_ORIGINS`/`trustedOrigins`; the comment in `cors.ts` should grow that warning when this lands.

## Recommendation and the contracts it implies

**Adopt Option A with the split-horizon CORS policy.** Keep Option B's shape (middleware + Global Config reusing the same resolve endpoint as data source) documented as the latency upgrade path if the extra RTT ever measurably hurts; nothing in A blocks that swap. Contracts:

1. **Resolve endpoint (new, public):** `GET /api/player-domains/resolve?host=<hostname>` — unauthenticated; `200 { "pairingCode": "ABC12" }` for a bound, verified host, `404` otherwise; CORS case 2 above (any origin, non-credentialed); `Cache-Control: public, max-age=<short TTL>` (rebind/revocation lag = TTL + next visit; browser HTTP cache serves repeat visits); rate-limit via the existing `clientAddress` hook (`apps/api/src/graphql/context.ts`). Returning the plain pairing code, not an opaque credential (rationale above).
2. **Player routing contract:** on the first-party host, `/` stays the splash and `/s/$code` is unchanged. On any other host, `/` (and per the standing decision, any path — paths never choose Devices) resolves by host: states `resolving` → `ready(code)`/`unbound` (holding page); errors map to the existing `PlayerState` error state. Studio's link/QR for a Device with a Custom Domain uses the bare `https://<domain>/`.
3. **CORS contract:** `applyCorsHeaders` (`apps/api/src/lib/cors.ts`) and yoga's `cors.origin` gain the two-case origin policy, always with `Vary: Origin`; `graphqlRequest` (`packages/graphql-schema/src/client.ts`) takes `credentials` in its options `Pick` so callers choose — Studio/Site keep `include`, the Player passes `omit`. `/api/realtime/auth` needs no change.
4. **Better Auth:** `trustedOrigins` unchanged, first-party only.

Ingress dependency, stated once: Option A needs only "bound hosts serve the Player SPA over TLS" — the minimum the ingress ticket must deliver anyway — which is why it is recommended ahead of that decision; Options B/C additionally require compute-before-static on the ingress and (for B's fast path) a replicated mapping store.
