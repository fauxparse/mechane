# Browser clipboard capabilities and interoperability limits

Research for ["Establish browser clipboard capabilities and interoperability limits" (#867)](https://github.com/fauxparse/mechane/issues/867), a child of the Show Editor clipboard map ["Design Show Editor clipboard and its import/export boundary" (#866)](https://github.com/fauxparse/mechane/issues/866).
Date: 2026-10-02. No live-browser experiments were run; every claim below comes from a fetched primary source (W3C Editor's Draft, vendor documentation, MDN compat data) and is labeled **specified** (spec text), **documented** (vendor or MDN implementation statements), or **untested** (no primary source found). This file inventories capabilities; it does not pick a clipboard format, a UX, or a browser-support policy.

## Repository policy check

That matters here: the Async Clipboard API is secure-context-only, so the existing HTTPS dev setup satisfies that requirement. Per the ticket, the facts below cover desktop Chrome, Safari, and Firefox without selecting support targets.

## The two clipboard mechanisms

**Specified** (Clipboard API and events, W3C Editor's Draft of 24 June 2026, hereafter "the spec"). The platform exposes one system clipboard with two access paths ([spec §1](https://w3c.github.io/clipboard-apis/#Cases)):

- **Clipboard Event API**: synchronous `copy`/`cut`/`paste` events carrying a `DataTransfer` in `ClipboardEvent.clipboardData`. Handlers read the clipboard in `paste` and write it by calling `setData()` then `preventDefault()` inside `copy`/`cut` ([spec §6.1-6.3](https://w3c.github.io/clipboard-apis/#override-copy)). Event handlers may write when the action comes from browser UI or an "allowed to show a popup" script context, and may read when the action comes from browser UI such as a Paste menu entry or keyboard shortcut ([spec §5.3.1-5.3.2](https://w3c.github.io/clipboard-apis/#allow-modify-clipboard)). Synthetic (script-dispatched) events must never touch the real clipboard.
- **Async Clipboard API**: `navigator.clipboard.read()`, `readText()`, `write()`, `writeText()` on a `[SecureContext]`-only attribute, gated by permission checks and user activation ([spec §7, §9](https://w3c.github.io/clipboard-apis/#async-clipboard-api)). Read permission requires transient activation plus interaction with a user-agent- or OS-created "Paste" element ([spec §9.1.1](https://w3c.github.io/clipboard-apis/#h-clipboard-read-permission)); write passes with transient activation plus a copy/cut element, or a granted `clipboard-write` permission ([spec §9.2.1](https://w3c.github.io/clipboard-apis/#h-clipboard-write-permission)).

The spec's permission model changed in 2025-2026: `clipboard-read` was removed as a Permissions-API name and `clipboard-write` remains ([spec §9](https://w3c.github.io/clipboard-apis/#clipboard-permissions); the removal is noted as spec issue references for `clipboard-write` in the `read`/`write` algorithm steps). Browsers have not converged on this. MDN's summary of the current split: Chromium prompts the `clipboard-read` permission when a spec-allowed read fails but the document has focus, and allows write with either `clipboard-write` granted or transient activation; Firefox and Safari instead show an "ephemeral context menu with a single 'Paste' option (which becomes enabled after 1 second)", require transient activation for writes, and do not support the `clipboard-read`/`clipboard-write` permissions "and not planned to be supported" ([MDN Clipboard API, Security considerations](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API#security_considerations)).

## Detail by ticket dimension

### User activation, permissions, and focus

- **Specified**: reads need transient activation plus a UA/OS "Paste" element, or they fail ([§9.1.1](https://w3c.github.io/clipboard-apis/#h-clipboard-read-permission)); the Async API "must not be available unless the script is executing in the context of a document that has focus" ([§11.2](https://w3c.github.io/clipboard-apis/#privacy-async)). Event-API access rides on the user's own copy/paste action, so no separate permission exists for it ([§5.3](https://w3c.github.io/clipboard-apis/#integration-with-other-scripts-and-events)).
- **Documented (Chrome)**: "clipboard access is only allowed when a page is the active tab. Pages in active tabs can write to the clipboard without requesting permission, but reading from the clipboard always requires permission", via the `clipboard-read` prompt; `clipboard-write` "is granted automatically to pages when they are the active tab"; `navigator.permissions.query({name:'clipboard-read', allowWithoutGesture:false})` reflects the state ([web.dev](https://web.dev/articles/async-clipboard#security_and_permissions)). Iframes need `allow="clipboard-read; clipboard-write"` ([web.dev](https://web.dev/articles/async-clipboard#permissions_policy_integration)); MDN repeats the Chromium-only Permissions-Policy requirement.
- **Documented (Safari)**: `clipboard.write`/`writeText` outside a user gesture "will result in the immediate rejection of the promise". Reads outside a gesture reject; reads pass if "the user is explicitly triggering a paste during the gesture (for instance `⌘V`)" or if "the contents of the system clipboard were written by a page with the same security origin". Otherwise WebKit shows platform UI (iOS callout bar, macOS context-menu Paste item); "tapping or clicking anywhere in the page (or performing any other actions, such as switching tabs or hiding Safari) will cause the promise to be rejected" ([WebKit blog, Security and Privacy](https://webkit.org/blog/10855/async-clipboard-api/)).
- **Documented (Firefox)**: `read`/`readText` "must be called within user gesture event handlers"; "a paste prompt is displayed when the clipboard is read. If the clipboard contains same-origin content, the prompt is suppressed" ([BCD notes on `api.Clipboard.read`/`readText`], mirrored in [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API#security_considerations)). Writes require a gesture.

Consequence for a Show Editor, with one distinction kept sharp: reading the `clipboardData` of a genuine user paste (or writing via a canceled `copy`) is event-API access and carries no clipboard permission in any browser; calling `navigator.clipboard.read()`/`readText()` from inside that same handler is a separate async read that still goes through read consent, even though the paste keystroke counts as the gesture (and, per the open bug below, mixing the two has its own Chromium hazard). For a toolbar Paste button, programmatic reads are possible everywhere but the consent surface differs per browser: Chrome asks a persistent permission, Firefox and Safari ask a per-action paste confirmation unless the clipboard content is same-origin-written (Firefox's documented suppression; Safari's same-origin-written grant). So same-origin Show tabs get promptless async reads in Safari/Firefox only while the clipboard still holds content written by a same-origin page and the gesture and focus conditions above are met; Chrome is prompt-once via its persistent grant. A keyboard Cmd/Ctrl+V into a focused canvas plus a `paste` listener needs no consent anywhere, because the user's own keystroke is the gesture and the data comes from the event, not from a permission-gated API.

### Secure contexts

- **Specified**: `Navigator.clipboard`, `Clipboard`, and `ClipboardItem` are `[SecureContext]`-only ([spec §7.1, §7.2 IDL](https://w3c.github.io/clipboard-apis/#async-clipboard-api)); WebKit confirms "`navigator.clipboard` is not present for `http://` websites" ([WebKit blog](https://webkit.org/blog/10855/async-clipboard-api/)).
- Repo fact: dev serves HTTPS via the checked-in Caddy config ([README.md:142](../../README.md)), so this constraint is already satisfied in development.

### MIME types, custom formats, and fidelity

- **Specified**: mandatory types are `text/plain`, `text/html`, `image/png` for both event and async paths ([§6.4](https://w3c.github.io/clipboard-apis/#mandatory-data-types-x)); optional types are `text/uri-list`, `image/svg+xml`, and any `"web "`-prefixed parseable MIME type ([§6.5](https://w3c.github.io/clipboard-apis/#optional-data-types-x)). A `write()` blob whose type is in neither list rejects with `NotAllowedError` ([§7.3.3](https://w3c.github.io/clipboard-apis/#dom-clipboard-write)). `image/png` must not be sanitized; `text/html` may be, unless the reader opts in via `read({unsanitized})` and the UA allows it ([§6.6](https://w3c.github.io/clipboard-apis/#unsanitized-data-types-x)).
- **Specified (custom format mechanics)**: `new ClipboardItem({'web application/x-foo': blob})` sets an `isCustom` representation; the OS write goes through a "web custom format map" (Windows "Web Custom Format Map", macOS `org.w3.web-custom-format.map`, Linux `application/web;type="custom/formatmap"`) plus numbered native entries, capped at 100 custom formats per write ([Appendix A](https://w3c.github.io/clipboard-apis/#algorithms)). Reads enumerate the map, so types round-trip by name.
- **Documented (Chrome)**: web custom formats are the recommended lossless channel "if you control both the copying and the pasting end" and need the payload "identical with the pasted data"; supported "on desktop and on mobile Chromium as of version 104" ([Chrome blog](https://developer.chrome.com/blog/web-custom-formats-for-the-async-clipboard-api)). Reading looks for `clipboardItem.types` entries that `startsWith('web ')`.
- **Documented (Safari)**: async read/write supports exactly four representations, `text/plain`, `text/html`, `text/uri-list`, `image/png`; custom pasteboard types were listed as future work in 2020 ([WebKit blog](https://webkit.org/blog/10855/async-clipboard-api/)). BCD 8.1.4 still marks the `web` type unsupported in Safari, so this has not shipped as of 2026-10.
- **Documented (Firefox)**: BCD marks the `web` type "preview" (Nightly/preview builds), and Mozilla's standards position on web custom formats is "position: positive" with "concerns: privacy" ([standards-positions #525](https://github.com/mozilla/standards-positions/issues/525), tracking [bug 1956304](https://bugzilla.mozilla.org/show_bug.cgi?id=1956304)).
- **Sanitization fidelity, documented**: HTML read back differs from HTML written: Chrome strips `<script>`, `<meta>`, `<head>`, `<style>` and inlines CSS ([Chrome unsanitized doc](https://developer.chrome.com/docs/web-platform/unsanitized-html-async-clipboard)); WebKit writes `text/html` through a JS-disabled document extracting "only visible content", stripping script, comments, `display:none`, and event-handler attributes, and on read strips hidden content such as comments and EXIF from images ([WebKit blog](https://webkit.org/blog/10855/async-clipboard-api/)). PNG bytes are not preserved either: browsers "re-encode images like PNGs" against decompression bombs; Chrome's own example shows a 68-byte input PNG read back as 161 bytes ([Chrome unsanitized doc](https://developer.chrome.com/docs/web-platform/unsanitized-html-async-clipboard)). Only the `web ` custom-format path is documented as byte-stable.

### Multi-representation payloads

- **Specified**: one `ClipboardItem` may carry several representations of the same logical item; different MIME types "describe different representations ... at different levels of fidelity", letting target apps choose ([spec §7.2](https://w3c.github.io/clipboard-apis/#clipboard-item-interface)). Platforms without multiple native clipboard items keep only the first ([spec §7.3](https://w3c.github.io/clipboard-apis/#dom-clipboard-write)). The default copy action "should create alternate text/html and text/plain clipboard formats when content in a web page is selected" ([spec §8.1](https://w3c.github.io/clipboard-apis/#copy-action)).
- **Documented (Safari)**: on Apple platforms type order is fidelity order: "types that come before other types are considered by the system to have 'higher fidelity'", native apps use it when picking a UTI ([WebKit blog](https://webkit.org/blog/10855/async-clipboard-api/)).
- **Documented (Chrome/Firefox)**: `write()` accepts a single `ClipboardItem`; passing more rejects `NotAllowedError` (BCD notes).

So a copy that writes `text/plain` plus `text/html` plus (on Chromium) `web application/x-mechane-…` in one item is the spec-shaped multi-representation pattern: external apps see plain/HTML, Chromium also gets the channel documented to round-trip bytes unchanged.

### Cross-tab, cross-browser, and cross-application portability

- **Specified**: the clipboard is the OS "system clipboard"; every write lands there ([spec §4 Model](https://w3c.github.io/clipboard-apis/#model)), so cross-tab and cross-app transfer is by construction: any tab or app reading the OS clipboard sees the flavors written. The spec's own caveat: "scripts should not assume that custom formats will be available to other applications on the system. For example, there is a limit to how many custom clipboard formats can be registered in Microsoft Windows" ([Appendix A note](https://w3c.github.io/clipboard-apis/#algorithms)). Linux "primary/secondary" selection clipboards are an open spec issue.
- **Specified (OS format mapping)**: `text/plain` maps to CF_UNICODETEXT / NSPasteboardTypeString / `text/plain` atom; `text/html` maps to CF_HTML / NSPasteboardTypeHTML / `text/html`; PNG to "PNG" / NSPasteboardTypePNG / `image/png` ([Appendix A](https://w3c.github.io/clipboard-apis/#algorithms)). On Windows, HTML travels as CF_HTML, a header-plus-fragment envelope ("Version:", "StartFragment:" offsets, `<!--StartFragment-->` comments) rather than the bare markup ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/dataxchg/html-clipboard-format)); the browser produces and parses this envelope.
- **Documented (Chrome)**: native apps see web custom formats under their platform names and "are not something that typical platform-specific applications understand"; apps must opt in for `web image/jpeg`-style formats ([Chrome blog](https://developer.chrome.com/blog/web-custom-formats-for-the-async-clipboard-api)). Same-browser round-trip works via the format map; cross-browser portability of `web ` formats is only as good as the other engine's support (Safari: no; Firefox: preview), so a Chrome-written custom format is unreadable in stable Safari/Firefox today, while the plain/HTML/PNG flavors written alongside it remain readable everywhere.
- **Documented**: Firefox and Safari suppress the paste prompt for same-origin clipboard content ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API#security_considerations), BCD notes); WebKit grants automatic programmatic access when "the contents of the system clipboard were written by a page with the same security origin" ([WebKit blog](https://webkit.org/blog/10855/async-clipboard-api/)). Chrome's equivalent friction reducer is the persistent `clipboard-read` grant.
- Within one Show tab or across Show tabs of the same origin, an async read is promptless in Safari/Firefox only while the clipboard still holds content written by a same-origin page and the gesture and focus conditions above are met; otherwise the paste UI appears. Chrome is prompt-once via its persistent `clipboard-read` grant. Reading the `paste` event's own `clipboardData` is promptless everywhere when the user performs the paste, because it never goes through read consent.

### Failure reporting

- **Specified**: permission failures reject with `NotAllowedError`; missing types reject `getType()` with `NotFoundError`; since the lazy-read model, a clipboard that changed between `read()` and `getType()` rejects with `InvalidStateError` rather than returning stale bytes ([spec §7.3.1, §7.2.3](https://w3c.github.io/clipboard-apis/#dom-clipboard-read)); unsupported write types reject `NotAllowedError` ([§7.3.3](https://w3c.github.io/clipboard-apis/#dom-clipboard-write)). Implementations "must handle scripts that try to place excessive amounts of data on the clipboard gracefully" ([§10.4](https://w3c.github.io/clipboard-apis/#nuisances)), with no defined size limit. `readText()` on a non-text clipboard resolves with an empty string ([MDN readText, guide](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API)).
- **Documented (Chrome 149+)**: stale `ClipboardItem` handles reject `InvalidStateError`; the guidance is to catch it, re-`read()`, and not cache `ClipboardItem`s; blobs already fetched remain valid ([selective-format-read blog](https://developer.chrome.com/blog/selective-format-read)).
- **Documented (Safari)**: a second overlapping `write()` makes "the previous invocation ... immediately reject"; undecodable image data rejects the write promise; read promises reject when the user dismisses the paste UI ([WebKit blog](https://webkit.org/blog/10855/async-clipboard-api/)).
- **Event API**: errors are structural rather than exceptions: a non-canceled `copy` writes the current selection instead of your data ([spec §6.1](https://w3c.github.io/clipboard-apis/#override-copy)); `getData()` for an absent type returns `''`; `DataTransfer` stored outside the handler must be a no-op ([spec §11.1](https://w3c.github.io/clipboard-apis/#privacy-events)).
- **Documented open bug**: reading a web custom format via `navigator.clipboard.read()` called inside a `paste` event handler returned a 0-byte Blob in Chromium ([issue 505045934](https://issues.chromium.org/issues/505045934), open as of 2026-10). Prefer one path per operation.

### What the paste event actually exposes

- **Specified**: the event's `clipboardData` is "a live but filtered view of the system clipboard, exposing mandatory data types the implementation knows the script can safely access" ([spec §5.1](https://w3c.github.io/clipboard-apis/#clipboard-event-interfaces)); mandatory read types are `text/plain`, `text/html`, `image/png` ([§6.4.1](https://w3c.github.io/clipboard-apis/#mandatory-data-types-x)). Custom formats through `DataTransfer` are left to implementations ("This is left to the implementation", [Appendix A](https://w3c.github.io/clipboard-apis/#algorithms)).
- **Documented**: Chromium exposes read-only files on paste for keyboard/menu pastes ([web.dev](https://web.dev/articles/async-clipboard)); WebKit documents its type list for the async API, not for events.
- **Specified**: reading a genuine user paste's own `clipboardData` carries no clipboard permission ([§5.3.2](https://w3c.github.io/clipboard-apis/#allow-read-clipboard)); an async `read()`/`readText()` invoked from inside that handler is a separate consent-gated operation, not part of the event's data access (see the activation section, and the Chromium bug in the failure section for why mixing them is risky).
- **Untested**: whether a given engine's `paste` event surfaces arbitrary custom types written by the same engine (the classic same-app DataTransfer round-trip) has no primary documentation for current Chrome/Safari/Firefox. Any design that depends on event-API custom types needs a live test matrix first.

## Specified versus implemented versus untested

- Specified only (no engine claims found): `clipboardchange` semantics outside Chromium; `presentationStyle` in Chrome; `text/uri-list` optional-type behavior beyond WebKit's 2020 list; Permissions-API `clipboard-write` descriptor interactions; the 100-custom-format write cap.
- Documented implemented: everything in the evidence table's version columns, from vendor pages, vendor release notes, or MDN BCD 8.1.4.
- Untested in this research: actual paste-event custom-type exposure per engine; Windows CF_HTML fragment-context fidelity when crossing into external apps (the format is documented, the mangling is not); OS-level payload size ceilings; behavior of other Chromium derivatives besides Edge (they track Chromium).

## Feasible choices for the later HITL tickets

Not decisions, just the option set the evidence supports.

1. **Plain text only** (`writeText`/`readText` plus `paste` event fallback). Works in all three browsers back to 2019-2024 versions, no prompts beyond read consent. A serialized fragment (JSON-as-text) travels as ordinary text wherever the OS clipboard carries text; programs that transform pasted text (editors normalizing whitespace or encoding) can change it, so hops through other applications are best-effort rather than guaranteed. The cost is human-unfriendly pastes elsewhere and total dependence on the app's own parsing. No engine documents rewriting `text/plain` (the spec permits sanitizing any non-PNG type, so this is absence of evidence, not a guarantee).
2. **Text pair: `text/plain` + `text/html` in one `ClipboardItem` or one `copy` handler.** All three browsers; external apps understand both flavors; Apple fidelity ordering makes HTML the richer flavor. Cost: every engine rewrites `text/html` on write and/or read (stripping elements, inlining CSS), so arbitrary embedded metadata is unsuitable unless the encoding survives a validated round-trip; it suits a human-readable rendering alongside a canonical channel, not as the canonical channel.
3. **Web custom format (`web application/x-mechane-…`) as the canonical channel.** The only browser-provided arbitrary typed format documented to round-trip bytes unchanged (unsanitized, spec-defined OS representation), and the Chrome-recommended pattern when both ends are yours. That is a channel guarantee, not a claim that JSON-in-text cannot preserve application data. Cost: Chromium-only in stable browsers (Chrome/Edge 104+; Safari not shipped; Firefox preview), so it needs a companion fallback flavor and a `ClipboardItem.supports('web application/x-mechane-…')` gate (supported C 121/S 18.4/F 127).
4. **Hybrid (options 2+3 combined in one write).** One `ClipboardItem` with `text/plain` (fallback), `text/html` (rich external paste), and `web ` (canonical). Single write, single consent, every consumer gets its best flavor. This is the spec's own multi-representation model; the cost is three serializations per copy and per-flavor parse on paste.
5. **Event-API-only (`copy`/`paste` with `DataTransfer`) for everything.** No permissions at all when the user drives the keyboard. Cost: reading is only possible inside a real user paste, custom types are implementation-defined, and synthetic events are useless, so toolbar buttons still need the async path or `document.execCommand` shims (deprecated per [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API)).

Downstream decisions this file deliberately leaves open: the actual MIME name and payload schema, whether the human-facing flavor is text or HTML, UX for paste consent in each browser, and any browser-support floor.

## Limitations

- Desk research only. No browser was driven; no clipboard bytes were inspected. Everything labeled untested above stays untested.
- Vendor statements have dates: WebKit's four-type list is from June 2020 and Safari may have changed unlisted behavior; BCD 8.1.4 (2026-10-01) is the freshness anchor for support matrices. The Chrome unsanitized doc says Chrome 120 where BCD says 122.
- Firefox details beyond BCD notes (paste-prompt wording, exact same-origin rule) come via MDN's summary rather than a Mozilla engineering page.
- Chrome 149's lazy-read change postdates most third-party writing on this API; the spec ED and the July 2026 Chrome blog are the only current descriptions, and Firefox has only a standards position, not an implementation.
