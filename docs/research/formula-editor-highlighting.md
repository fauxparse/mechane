# The Formula editor: CodeMirror 6 with a Lezer grammar, a spreadsheet-language fork, or a hand-rolled overlay

Research for [#666](https://github.com/fauxparse/mechane/issues/666), part of map [#664](https://github.com/fauxparse/mechane/issues/664); input to the Transformer authoring-surface and validator tickets.
Date: 2026-09-22. Claims cited to primary sources (npm registry metadata, package source on GitHub, the official CodeMirror and Lezer docs, MDN), plus first-hand measurements made for this research: a Lezer grammar for JEXL's surface was written and generated, and every bundle figure below was produced by bundling the actual packages with esbuild 0.28.2 (`--bundle --minify --format=esm`, gzip -9) in a scratch project. Method is reproducible from the cited package versions.

## The question

#664 settled that Formulas are a vendored JEXL with an Excel-flavoured Function catalogue, that JEXL's lexer is not Lezer and exposes no CodeMirror token stream, and that "the editor grammar and the evaluator grammar are two artifacts that can drift, and something has to hold them together." Studio today contains no text-editing infrastructure at all — every manifest is free of CodeMirror, Monaco, Prism, Shiki, Lezer and highlight.js, and all Studio editing is native `<input>`/`<textarea>`. So the route is chosen from zero: which route buys source highlighting, autocomplete, and inline diagnostics driven by _our_ validator, at what Studio bundle cost, and how badly does each route worsen the two-grammars drift?

## Headline findings

1. **Recommendation: CodeMirror 6 with a hand-written Lezer grammar, with correctness taken from the vendored evaluator, not the editor tree.** The Lezer grammar exists to colour and to give completion its context; a `@codemirror/lint` source runs the vendored JEXL parser itself over the document, so inline diagnostics are exact by construction; a `CompletionSource` serves the node's named input ports and the Shape fields beneath them. The trade-off is the bundle: a complete editor stack measures **125 KB gzipped**, roughly two `@xyflow/react`s, and a new dependency family in a repo with none — mitigated by lazy-loading the editor chunk so the cost lands only when a Formula inspector opens.
2. **The grammar is a day's work, measured, not estimated.** This research wrote a faithful Lezer grammar for JEXL's entire expression surface (all 20 stock operators including `in`, `|` transforms, filters, ternary, object/array literals, both quote styles, JEXL's Unicode identifier class): **107 lines / 2.8 KB of `.grammar` generating a 5.0 KB parser**. It passed a 20-case corpus spanning the ticket's examples (`SUM(candidates.votes)`, chained relative filters, transform chains, ternary chains) — and the exercise itself surfaced two genuine JEXL subtleties the first draft got wrong (call-after-filter, leading-dot relative identifiers), which is the drift problem demonstrated in miniature.
3. **`codemirror-lang-spreadsheet` is not a shortcut.** It _does_ tolerate bare identifiers (`my_range` parses as a `NameToken` reference — its own test corpus proves it), and it is MIT. But its grammar is Excel's, not JEXL's: `candidates.votes` tokenizes as **one** name (dots are name-continuation characters), `b2` is a cell reference, `1:2` is a range token, `==`/ternary/`&&`/`||`/pipes/single-quoted strings do not exist, and a space between two references is the _intersection operator_. It ships **no autocomplete** (the demo app hand-rolls that). A fork bundles at **126.6 KB gzipped versus 125.0 KB for writing our own** — the fork buys nothing but its test-file format. Unmaintained since 2023-05.
4. **The hand-rolled overlay is an order of magnitude cheaper and an order of magnitude more bespoke.** The industrialized form of the technique (`react-simple-code-editor`, 636k downloads/week, MIT) measures **6.7 KB gzipped**. But completion needs caret coordinates a `<textarea>` will not give you (no API exists; the standard workaround is a mirror div re-measuring the text up to `selectionStart`), diagnostics need hand-positioned wavy underlines, and there is no structural agreement with the evaluator at all unless the vendored parser is run in-browser — which, notably, _is_ the strongest available diagnostics story regardless of route.
5. **Monaco and ACE are measured out.** Monaco's core-only bundle is **677 KB gzipped** (1.15 MB with languages) and needs web workers; ACE core measures **120 KB gzipped** — CM6's weight with none of its parsing. CodeMirror's own `basicSetup` metapackage (124.7 KB gzipped) measures the same as a minimal bespoke configuration, confirming that CM6's floor is the DOM layer, not the extras.

| `@lezer/generator` (build-time only)               | 1.8.0                  | 2025-06-23                     | MIT     |

Lezer is "maintained by the CodeMirror team" ([lezer.codemirror.net](https://lezer.codemirror.net/)), so the whole stack is one project's dependency family, not a coalition.

**`@codemirror/language`** — `LRLanguage.define({parser, props})` wraps a generated Lezer parser; `syntaxHighlighting(HighlightStyle)` wires a tag→class stylesheet; `styleTags` in the parser props maps grammar nodes onto `@lezer/highlight` tags. `syntaxTree(state)` returns "the current (possibly incomplete) parse tree of the active language" — this is how a completion source or our validator walks identifier nodes without re-tokenizing ([language reference](https://codemirror.net/docs/ref/#language)). The same package also carries `StreamLanguage` for CM5-style stream parsers — that variant is evaluated in §5.

**`@codemirror/lint`** — the package is designed around exactly the ticket's "the checker is ours, not the editor's" shape. `linter(source)` takes a `LintSource = fn(view) → readonly Diagnostic[] | Promise<readonly Diagnostic[]>`; "it will be called whenever the editor is idle (after its content changed)" after a configurable delay (default 750 ms). A `Diagnostic` is `{from, to, message, severity: "error" | "hint" | "info" | "warning", actions?}` — positions are document offsets, rendered as inline squiggly mark decorations plus a hover tooltip; `lintGutter()` adds per-line markers. For diagnostics produced _outside_ the editor (a publish-gate validator, a server check), `setDiagnostics(state, diagnostics)` "returns a transaction spec which updates the current set of diagnostics" — so results can be pushed in from React state rather than polled ([lint reference](https://codemirror.net/docs/ref/#lint)).

**`@codemirror/autocomplete`** — `CompletionSource = fn(context) → CompletionResult | Promise<CompletionResult | null> | null` may be async, so a completion round-trip through the GraphQL cache or a live-data subscription is native. `context.matchBefore(regex)` / `tokenBefore(types)` give the word being completed from the _syntax tree_ (so `candidates.|` can offer Shape fields while `|` offers transform names — different tree nodes); each `Completion` carries `label`, `type`, `detail`, `info`, `apply`, and `validFor` for cheap re-filtering as typing continues. `autocompletion({override: [source]})` installs one ([autocomplete reference](https://codemirror.net/docs/ref/#autocomplete.autocompletion)).

**`@lezer/generator`** — a build-time CLI (`lezer-generator grammar.grammar -o parser.js`) with no runtime cost. The grammar language gives named `@precedence` groups with associativity, `@specialize` for keyword/identifier disambiguation, external tokenizers for what regexes cannot express, and node props for highlighting ([generator guide](https://lezer.codemirror.net/docs/guide/)). Two properties matter most for an editor over an untrusted-in-progress document: it is **incremental** ("can quickly re-parse documents that were slightly changed… by reusing nodes from the old parse") and **error-insensitive** ("the parser is equipped with strategies for recovering from syntax errors, and can produce a tree for any input") — a half-typed Formula still highlights and still carries completable structure, and `node.type.isError` ([`@lezer/common`](https://lezer.codemirror.net/docs/ref/#common.NodeType.isError)) marks exactly the spans the editor tree itself disagrees with.

## 2. The measured grammar: a Lezer grammar for JEXL's surface

JEXL's surface was taken from its source, not its README: the element table with precedences in [`lib/grammar.js`](https://github.com/TomFrost/Jexl/blob/master/lib/grammar.js), the token regexes in [`lib/Lexer.js`](https://github.com/TomFrost/Jexl/blob/master/lib/Lexer.js), and the operand/binop/filter/transform state machine in [`lib/parser/states.js`](https://github.com/TomFrost/Jexl/blob/master/lib/parser/states.js). That surface is:

- **Operators with precedences from the element table**: `||`/`&&` (10); `==`/`!=`/`>`/`>=`/`<`/`<=`/`in` (20); `+`/`-` (30); `*`/`/`/`//` (40); `%`/`^` (50); unary `!`; unary minus is not an operator at all — the lexer folds `-` into the following numeric literal after an operator, `(`, `[`, `?` or `:`.
- **Literals**: strings in single _or_ double quotes with only `\'`, `\"`, `\\` escapes; numbers `[0-9]*\.[0-9]+ | [0-9]+` (so `.5` is valid, `5.` is not, and there is **no exponent form** — `1e3` lexes as the number `1` followed by the identifier `e3`); booleans `true`/`false`; **no null literal**.
- **Identifiers**: Unicode — starts with `a-zA-Z`, Cyrillic `а-яА-Я`, Latin-1 supplement letters, `_` or `$`; continues likewise plus digits. `in` is a word operator (wrapped in `\b` by the lexer), so **a port cannot be named `in`** — it lexes as the operator.
- **Structure**: dot member access; `[expr]` subscript and filter (identical syntax — filters are subscripts whose expression uses leading-dot _relative_ identifiers, e.g. `employees[.age >= retireAge]`); function calls `f(args)`; transform pipes `x|upper`, `x|split(' ')[1]`, binding tighter than every binary operator but looser than unary `!` (from `states.js`: pipes are reachable from operand states, never from `expectOperand`); ternary `? :`; object literals `{key: value}` with bare-identifier or quoted keys; array literals. Calls are legal after identifiers and after filters (`a[0](3)` — the filter state machine returns to `identifier`, which accepts `(`), but not after parenthesized expressions or argument lists.

The grammar written for this research covers all of that in **107 lines / 2,755 bytes of `.grammar`**, generating a **4,998-byte parser** plus a terms file. It passed 20/20 of a corpus that includes `SUM(candidates.votes) & " votes for " & name`, chained relative filters (`employees[.age >= 30 && .age < 40][.age < 35]`), nested ternaries, transform chains, `in`, `.5 * 2^3 % 4 // 2`, object/array literals, and — on the reject side — `a ==`, `SUM(`, `in` alone, `true false`, an unterminated string. Two findings from writing it are directly relevant to the drift question:

1. The first draft disallowed calls after filters (`a[0](3)`), which JEXL's state machine permits. Only reading `states.js` caught it.
2. JEXL's minus-folding means the two lexers _legitimately disagree_ on token boundaries: `a * -1` is three evaluator tokens (`a`, `*`, literal `-1`) but a natural grammar yields four (`a`, `*`, unary `-`, `1`). Any conformance comparison must normalize unary minus first — see §7.

One genuine open slot for the Function-catalogue ticket: **where `&` sits in the precedence table** (added via `addBinaryOp`, which writes into the same element map). This research's grammar provisionally put it with `%`/`^`; the decision belongs to the catalogue, and the corpus must pin whichever level is chosen.

## 3. `codemirror-lang-spreadsheet`: what forking would actually mean

State, from primary sources: GitHub repo `luizzappa/codemirror-lang-spreadsheet`, created 2023-03-18, last pushed **2023-05-25**; npm `codemirror-lang-spreadsheet` latest **1.3.0 published 2023-04-16**, ~6.9k downloads/month, **MIT**, 11 stars, 1 open issue, not archived. Effectively dormant for three and a half years. It is built on the XLParser Excel grammar (the README cites the ["A Grammar for Spreadsheet Formulas Evaluated on Two Large Datasets"](https://fenia266781730.files.wordpress.com/2019/01/07335408.pdf) paper and [XLParser](https://github.com/spreadsheetlab/XLParser)), and its dist is 18.3 KB ESM.

**Bare identifiers: tolerated, but as _named references_, and that is where the trouble starts.** The test corpus ([`test/References.txt`](https://github.com/luizzappa/codemirror-lang-spreadsheet/blob/main/test/References.txt)) shows `my_range` and `myTRUErange` parsing as `Reference(ReferenceItem(NameToken))`. But the grammar's [`NameToken`](https://github.com/luizzappa/codemirror-lang-spreadsheet/blob/main/src/syntax.grammar) is:

```
NameToken { $[a-zA-Z\\_] $[a-zA-Z0-9_\\\.?€]* }
```

Dots and question marks are _continuation characters_. So `candidates.votes` — the map's own canonical auto-mapping example — tokenizes as **one name blob**: no member access is visible to highlighting, completion cannot split `candidates` from `votes`, and `a?.b` likewise disappears into a single token. Meanwhile `CellToken { column row }` makes any port named like `b2` or `ab12` a cell reference, and `HorizontalRangeToken { row ":" row }` makes the `1:2` inside `x ? 1:2 : 3` a range token. Excel-isms with no Formula meaning are load-bearing: a space between references is the intersection operator (an external tokenizer in [`src/tokens.ts`](https://github.com/luizzappa/codemirror-lang-spreadsheet/blob/main/src/tokens.ts)), `&` is already Excel's concatenation operator (a happy accident, but at Excel's precedence), `%` is a _postfix percent_ operator, `=` is both the formula prefix and equality, and there is no `==`, no ternary, no `&&`/`||`, no `|` pipe, no single-quoted string, no object/array literals, and no bracket subscripting at all. The `Function` token requires the paren to be glued to the name (`$[a-zA-Z_]+ $[a-zA-Z_0-9.]* OpenParen`), so `SUM (x)` does not tokenize as a call.

**Adding/removing token classes** is two different jobs: retagging an existing node is one line in the `styleTags` map in `src/index.ts`; changing what _tokens exist_ means editing `syntax.grammar` and regenerating the parser with `@lezer/generator` (the repo ships the rollup wiring). Note the `styleTags` map and indent/fold props reference node names (`NumberToken`, `Application`) that no longer exist in the grammar — dead entries, harmless but symptomatic. The idiom/decimal-separator handling is **module-global mutable state** (`setLezerIdiom`/`setDecimalSeparator` reconfigure tokenizers for every editor at once), which we would strip.

**The autocomplete claim corrects to zero**: the npm package contains no completion code (grep of `dist/index.js`: 0 hits). The README points at a separate demo app, [`codemirror-app-spreadsheet`](https://github.com/luizzappa/codemirror-app-spreadsheet), whose `autocompletion.ts` is a hand-written `CompletionSource` fetching a JSON list of Excel function names — i.e. the same bespoke source we would write anyway.

**Fork cost measured**: the full editor stack with this package in place of our own grammar bundles to 390,504 raw / **126,601 gzipped** bytes, versus 381,932 / **125,041** for the hand-written grammar — the language package (18.3 KB raw) outweighs our generated parser (5.0 KB) outright. Since retaining the fork also means rewriting most productions (delete A1/range/sheet/union/intersection machinery; add ternary, logic operators, pipes, filters, JEXL strings, JEXL identifiers, bracket subscripting), the honest fork estimate is "keep the `fileTests` corpus format, rewrite the grammar" — which is the hand-written route wearing a different commit history.

## 4. The hand-rolled overlay, industrialized and from scratch

The technique: a `<textarea>` whose text is made transparent, layered exactly over a `<pre>` (or `<div>`) rendering the same text with highlight spans; the textarea keeps native selection, caret, IME composition, scrolling and accessibility. The industrialized form is [`react-simple-code-editor`](https://github.com/react-simple-code-editor/react-simple-code-editor) — MIT, 636k downloads/week, last published 2024-07-04 — which measures **17.5 KB raw / 6.7 KB gzipped** (React excluded; Studio already ships React). Its README is the most candid primary source on the approach's costs:

> "It works by overlaying a syntax highlighted `<pre>` block over a `<textarea>`. When you type, select, copy text etc., you interact with the underlying `<textarea>`, so the experience feels native."

> Limitations: "The syntax highlighted code cannot have different font family, font weight, font style, line height etc. for its content… changing anything that affects the layout can misalign it." "We hide text in the textarea using `-webkit-text-fill-color: transparent`." "The editor is not optimized for performance and large documents can affect the typing speed." Tab insertion and undo are re-implemented by hand because programmatic updates destroy the browser undo stack.

What #666's three capabilities cost on this route:

- **Highlighting** — a tokenizer over the Formula text. Crucially, the tokenizer can _be the vendored JEXL lexer's own regexes_ (`preOpRegexElems`/`postOpRegexElems` in `lib/Lexer.js`), which makes token-level drift structurally impossible rather than merely tested-for. Order-1 KB of our own code.
- **Inline diagnostics from our validator** — two layers. Underlines are highlight spans carrying `text-decoration-line: underline; text-decoration-style: wavy` ([MDN, `text-decoration-style`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-decoration-style)) over the offending offsets — workable in a monospace overlay, fragile the day anyone wants proportional fonts. The _positions_, though, can be exact: the vendored evaluator is a plain synchronous tokenizer+parser in `packages/domain`, so the browser can run the real parser over the text and underline exactly where it objects. This is the route's sleeper strength — it holds for §6's CM6 recommendation too.
- **Completion from live data** — the expensive part. `HTMLTextAreaElement` exposes `selectionStart`/`selectionEnd`/`setSelectionRange`/`setRangeText` and nothing that returns caret _pixel_ coordinates ([MDN, `HTMLTextAreaElement`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLTextAreaElement)); positioning a popup at the caret requires the mirror-div trick (a hidden div with copied computed styles, re-rendering the text up to the caret and measuring it). Popup list-box keyboard navigation (arrows, Enter, Escape, typing-ahead) is all hand-rolled, and it is exactly the kind of code CM6's 27 KB gzipped `@codemirror/autocomplete` already is.

Net: roughly 10–15 KB gzipped of our own code and no new dependency, against an unbounded tail of bespoke editor behaviours (multiline growth, IME edge ordering, undo coalescing, popup focus management) that the overlay README itself enumerates.

## 5. The other current options, measured

Two further routes were priced rather than guessed. **CodeMirror 6 with `StreamLanguage`** (a CM5-style stream tokenizer instead of a Lezer grammar — no grammar file, no generated parser, no syntax tree) bundles highlight-only at 278,243 raw / **90,564 gzipped**: 34.5 KB gzipped cheaper than the Lezer route, but the saving is exactly the tree — no `syntaxTree` for completion context, no structural conformance with the evaluator (token agreement only), no incremental reparse. **Monaco** measures 2,637,655 raw / **677,363 gzipped** via `editor.api` with _no_ languages or contributions, and 4,433,520 / **1,147,121** as the standard `editor.main` — plus it wants web workers for its intended mode; it is a code IDE, and a Formula field is not one. **ACE** (`ace-code` 1.44.0, BSD-3-Clause, still publishing — May 2026) cores at 423,243 / **120,180 gzipped**: CM6's weight class with a regex-mode tokenizer instead of a parser. Read-only highlighters (Prism, Shiki) are not editors and do not address diagnostics or completion; they would only colour a rendered Formula, which the overlay route already does for free.

**Recommendation: CodeMirror 6 with a hand-written Lezer grammar.** The evidence: the grammar is small and now de-risked by construction (§2); lint and autocomplete are designed around exactly our division of labour — external checker, live-data completion (§1); every alternative is either the same weight for less capability (ACE, StreamLanguage), the same weight for the wrong language (the spreadsheet fork), two orders of magnitude heavier (Monaco), or an order of magnitude lighter with unbounded bespoke surface (the overlay). Two design commitments make it land well:

1. **The editor tree is for display and completion context only. Correctness comes from the vendored evaluator.** The lint source runs `packages/domain`'s vendored JEXL parser over the document text — the same artifact the server will evaluate and the publish gate will validate — so a diagnostic can never disagree with the evaluator about what parses or what a name resolves to. The Lezer grammar then only has to be _highlighting-faithful_, and drift degrades colours, never correctness.
2. **Lazy-load the editor.** The Formula inspector is not the first screen; a dynamic `import()` puts the 125 KB behind the first inspector open. Amortization improves further because the substrate serves ADR-0010's two later surfaces (event payload and property expressions).

**The trade-off stated plainly:** 125 KB gzipped (≈2× `@xyflow/react`, ≈0.2× Monaco's floor) and eight new MIT packages from one maintained family, in a repo that today ships no editor at all; plus a second grammar to keep honest (§7). If that cost is later judged unacceptable, the fallback is the overlay with the vendored lexer's regexes and the vendored parser for diagnostics — accepting bespoke completion and cosmetic-only conformance — not the spreadsheet fork, which this research found strictly dominated.

## 7. Keeping the editor grammar and the evaluator in agreement

What each route implies for drift:

- **CM6 + Lezer**: two real grammars, both declarative, both machine-comparable — the only route where structural conformance is even expressible. With §6's commitment (lint = vendored parser), the blast radius of drift shrinks to highlighting and completion context; the corpus below keeps even that honest.
- **StreamLanguage / overlay**: no structure to compare — conformance collapses to token streams. Reusing the vendored lexer regexes makes token drift near-impossible, but nothing checks structure; that is acceptable only because the vendored parser supplies diagnostics.
- **Spreadsheet fork**: a third grammar from a different language — maximal drift by design; even its token boundaries differ (dots inside names).

**Conformance corpus sketch.** A checked-in corpus of Formula sources with golden outputs from _both_ engines, diffed in CI; regenerating the goldens must be a visible, reviewable step whenever either grammar or the element table changes. It must cover:

1. **Token-kind agreement**: each entry tokenized by the vendored `Lexer` and by the Lezer parser's leaves, normalized — unary minus folded to match JEXL's literal-folding; `in` mapped operator-vs-identifier; `1e3` asserted to split as `1` + `e3` in _both_; `?.`/dots asserted to split into member access in the Lezer tree (the spreadsheet grammar's failure mode, pinned as a regression).
2. **Accept/reject agreement**: every evaluator-parseable Formula yields a zero-error-node Lezer tree; every evaluator parse error yields ≥1 error node. This is the publish-gate invariant: the editor must never look clean on a Formula the server will reject, nor underline a Formula the server accepts.
3. **Precedence and shape**: one entry per precedence level and per associativity question — `a||b&&c`, `a==b<c+d*e^f%g`, `x ? y : z ? w : v` (right-assoc), `in` chains, `&` at its catalogue-decided level, `a + b|t` (pipe tighter than `+`), `!x|t` (unary tighter than pipe), `a[0](3)` (call after filter — the bug this research's own first draft had), no call after parens `(...)(...)`.
4. **Filters and relatives**: `[0]`, `[expr]`, leading-dot relatives `.age >= retireAge`, chained filters, filter inside ternary/object/array.
5. **Literal edges**: `.5`, `5.0`, `5.` (rejected), both quote styles with `\'` `\"` `\\` escapes and escapes that are _not_ there (`\n` is literal), unterminated strings, Cyrillic/Latin-1/`$` identifiers, booleans, empty and whitespace-only documents (editor accepts, validator diagnoses "empty Formula").
6. **Corpus mechanics**: golden files of `source → token dump (both) → AST dump (both) → accept/reject`; a CI job that regenerates and diffs; and, strongest form, the operator token list _derived from_ the vendored `grammar.js` elements table so adding a `addBinaryOp`-style operator cannot leave the editor grammar behind — one data table, one generated artifact, one hand-written one, all held to the same corpus.
