Deploying Mechanē to Vercel

What it takes to get Studio, Player and the API running on mechane.live this weekend, backed by Neon Postgres, Cloudflare R2 and Ably. Only the email verification switch has been built. Nothing is deployed.

Summary

Studio and Player are close. They're plain Vite SPAs and need a rewrite rule and some environment variables. The API is further off: three code problems still block a working production deploy, and a fourth is now handled.

  1. The API won't build on Vercel.

    @vercel/node 5.9.5 transpiles functions with whatever typescript package the project has installed, and calls ts.sys.readFile and ts.transpileModule. This repo is on TypeScript 7.0.2, which has neither. In apps/api, require('typescript').transpileModule is undefined.

  2. The Cron drain from ADR-0015 doesn't exist.

    The ADR and PRD §4.4 both say production needs a protected drain endpoint on a Vercel Cron schedule. No such route exists, and there's no vercel.json in the repo. The drain that runs right after each change does exist, so the normal case works. A publish that fails is never retried.

  3. Images go through functions, and Vercel caps function bodies at 4.5 MB.

    The cap covers both request and response (Vercel function limits). DEFAULT_IMAGE_UPLOAD_POLICY allows 25 MB uploads and 10 MB processed images. Both PUT /api/uploads/* and GET /api/images/* go through functions, so anything over 4.5 MB fails either way.

  4. No email gets sent. Handled

    sendEmail only writes to the log. Verification can now be switched off with REQUIRE_EMAIL_VERIFICATION=false. Real email is tracked in #759.

There are also smaller config issues: DNS, SPA rewrites, the Player's hardcoded API URL default, pnpm 11 on Vercel, and the Node version. Each is covered below.

Decisions

Domain: mechane.live

The three apps have to share one registrable domain. Studio calls the API with credentials: "include" and relies on Better Auth's session cookie. Browsers treat *.vercel.app as a public suffix, so two vercel.app URLs count as different sites and sign-in fails. Subdomains of mechane.live are the same site, so the cookie is sent.

No clash with local dev

Local dev stays on mechane.dev. Your Mac's dnsmasq and /etc/resolver/mechane.dev send that name to 127.0.0.1, and neither touches .live. Leave the local setup alone.

Why the cron schedule is an env var

A per-minute cron expression fails deployment on Hobby. The API build reads its schedule from CRON_SCHEDULE and defaults to daily. After upgrading, you only change that variable.

I haven't confirmed what Ably does when you go over the connection limit. Expect extra Players to fail to connect. Check the Ably dashboard's stats after rehearsals.

Email: off for launch Done

Production runs with REQUIRE_EMAIL_VERIFICATION=false. New email/password accounts are signed in right after sign-up, and no verification email is sent. Leaving the variable unset keeps verification required, so local dev and CI behave as before.

Setting up a provider, the Studio UX changes, and turning verification back on are tracked in #759. The issue also covers accounts created while verification is off: they have email_verified = false, and Better Auth would block their password sign-in the moment verification comes back on.

Image size

For the weekend, lower the limits to 4 MB so they fit under Vercel's cap. The proper fix is to have ImageUploadPlan.url return a presigned S3 PUT URL and serve images from the bucket or a CDN. The GraphQL shape (method, url, requiredHeaders) already allows that, but it's too much for a weekend.

Code changes

Do these in order. Items 1 to 3 block the deploy, item 4 is done, and the rest are config.

Blocker1. Bundle the API yourself

Replace Vercel's automatic handling of apps/api/api/*.ts with a build step. It bundles the API with esbuild and writes Build Output API files. That gets around the TypeScript 7 crash. I expect it also avoids two other failures, though I haven't reproduced them:

  • The package is "type": "module" but its imports have no file extensions (../src/graphql/server). Node's ESM loader can't resolve those at runtime.
  • The workspace packages (@mechane/domain, @mechane/realtime, @mechane/commands) export raw .ts files.
  1. Move the request routing out of apps/api/src/dev-server.ts into a shared src/http-handler.ts that exports (req, res) => Promise<void>. It covers auth, GraphQL, uploads, images and realtime auth. dev-server.ts already routes everything in one createServer callback, so this is mostly moving code. The WebSocket upgrade listener and the internal publish route stay dev-only.
  2. Add a Vercel entry file that imports the handler and calls attachDatabasePool(pool) from @vercel/functions (see item 5).
  3. Add a build:vercel script that:
    • bundles that entry into .vercel/output/functions/api.func/index.mjs (platform node, format esm, with pg-native, bufferutil and utf-8-validate marked external);
    • writes .vc-config.json next to it with { "runtime": "nodejs22.x", "handler": "index.mjs", "launcherType": "Nodejs" };
    • writes .vercel/output/config.json containing version: 3, a route that sends /api/(.*) to /api, and a crons entry whose schedule comes from CRON_SCHEDULE (default 0 4 * * *).
  4. Delete apps/api/api/. Its five entry files copy dev-server.ts, and they've already drifted from it: the dev server has a publish route the functions lack.

Check that req.url inside the function still carries the original path (/api/graphql, not /api). The router depends on it. Log it once on the first deploy.

A cheaper option is to pin apps/api to typescript@5.9.3, as packages/graphql-schema already does. That fixes the crash but leaves the ESM and workspace-.ts risks untested. If you try it, run vercel build locally before relying on it.

Blocker2. Add the cron drain

Add GET /api/cron/player-invalidations to the handler.

  • Reject the request unless Authorization equals Bearer ${CRON_SECRET}. Once that env var is set, Vercel sends the header on every cron call.
  • Call drainPlayerInvalidations() from src/db/player-invalidation-outbox.ts in a loop until a batch claims nothing or a time budget runs out. Then return the counts. ADR-0015 requires bounded batches because functions have a maximum duration.
  • Take the schedule from CRON_SCHEDULE at build time. The default is 0 4 * * *, which Hobby accepts. Switch to * * * * * after upgrading to Pro.

Blocker3. Lower the image limits

In packages/domain/src/images.ts, set maxSourceBytes and maxNormalizedBytes to 4 * 1024 * 1024. Studio gets these limits from GraphQL's ImageUploadConstraints and the design-system validator, so the "must be smaller than N MB" message updates without further changes. Update any tests that check the old numbers.

Done4. Email verification switch

apps/api/src/auth.ts now reads REQUIRE_EMAIL_VERIFICATION. Only the exact value false turns verification off, and that setting also stops verification emails going out on sign-up. apps/api/.env.example documents the variable. Checked against the test database:

Config5. Postgres connections

src/db/client.ts creates a pg Pool when the module loads. On Vercel:

  • Point the runtime DATABASE_URL at Neon's pooled connection string.
  • Call attachDatabasePool(pool) from @vercel/functions, so idle clients close before an instance suspends. Otherwise connections leak slowly.
  • Run migrations with the unpooled string.

Config6. Studio and Player

  • Add a vercel.json to apps/studio and apps/player with { "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }. Without it, deep links and reloads on TanStack Router paths return 404.
  • The Player's default API URL in production is https://api.mechane.dev (apps/player/src/api-url.ts:1). Local dev uses the same constant when the Caddy proxy is on, so leave it. Set VITE_API_URL=https://api.mechane.live on the Player project instead.
  • Don't set VITE_DEV_PROXY on Vercel. In a production build it switches the Player from Ably back to the local WebSocket (shouldUseRealtimeSocket).

Config7. Housekeeping

  • Add .vercel to .gitignore. vercel link creates that folder.
  • .tool-versions pins Node 26.8.1, but CI uses 22. Set Node 22.x on all three Vercel projects, matching CI and the runtime in .vc-config.json.
  • Vercel doesn't officially support pnpm 11. Set ENABLE_EXPERIMENTAL_COREPACK=1 on every project so Vercel uses the "packageManager": "pnpm@11.5.2" pin (Vercel corepack changelog). Some users report Corepack still picking an older pnpm. If the install then fails on pnpm-workspace.yaml (allowBuilds is pnpm 11 syntax), override the Install Command with npx pnpm@11.5.2 install --frozen-lockfile.

Turn preview deployments off for now

Previews get *.vercel.app URLs. Those aren't in the CORS allowlist (apps/api/src/lib/cors.ts matches exact origins) and hit the cookie problem above. Worse, a preview that inherits the production DATABASE_URL lets a branch build write to production data. If you keep previews, scope every env var to Production only.

Weekend order of work

Checkboxes save in this browser, so you can tick things off as you go.

Friday evening

Accounts, and anything that waits on DNS
  • Create the three Vercel projects and add their mechane.live subdomains. Then create the CNAMEs (and a CAA record, if needed). Certificates can't be issued until DNS resolves, so do this first.
  • Configure the projects, but don't deploy yet. Set root directories, turn off previews, and set ENABLE_EXPERIMENTAL_COREPACK.
  • Create the Neon database through the Marketplace and attach it to the API project.
  • Create the R2 bucket and token, and the Ably app and key.

Saturday

Code, then the first deploy
  • Make code changes 1 to 3 and 5 to 7 on a branch. Open a PR and merge once CI passes. The email switch (item 4) is already in the working tree.
  • Apply migrations from your laptop: 
    DATABASE_URL='<neon unpooled url>' pnpm --filter @mechane/api db:migrate
  • Build the API locally first. In apps/api, run vercel link, vercel pull, then vercel build --prod. Check that .vercel/output/config.json has the route and the cron.
  • Enter the env vars, deploy the API, and run the API checks.
  • Deploy Studio and Player.

Smoke test

API

  • curl -i https://api.mechane.live/api/graphql -H 'content-type: application/json' -d '{"query":"{ __typename }"}' returns 200.
  • curl -i -X OPTIONS https://api.mechane.live/api/graphql -H 'Origin: https://studio.mechane.live' -H 'Access-Control-Request-Method: POST' echoes the origin in Access-Control-Allow-Origin.
  • curl -i https://api.mechane.live/api/cron/player-invalidations -H "Authorization: Bearer $CRON_SECRET" returns drain counts. Without the header it returns 401.
  • The Vercel dashboard lists the cron job under the API project.

Studio

  • Sign up. You land in Studio signed in, with no verification step. Reload, and you're still signed in. That shows the session cookie works across subdomains.
  • Open a Show's URL directly and reload. It loads instead of returning 404.
  • Upload an image of about 3 MB and check that it shows. Then upload a 6 MB image: you should get the size error, not a 413 from Vercel.

Player and realtime

  • Publish a Show and start a Run. On a phone, open the Player with the pairing code or QR code.
  • Change a live value in Studio. The phone updates without a reload, and the Ably dashboard shows the connection.
  • Put the phone in airplane mode, make a change, then reconnect. The Player catches up.

Limits at launch

  • No email. Anyone can sign up with an address they don't own. Password reset links only appear in the Vercel logs, so resetting a password means you fetch the link by hand. #759 fixes both.
  • Images up to 4 MB. Each uncached image request runs a function. Browsers cache the response for a year, but function calls and bandwidth still count against the plan.
  • 200 Players at once on Ably Free.
  • Up to a day to recover a missed update, until you move to Vercel Pro.
  • Cold starts. The first request after a quiet spell waits for a new instance to start and open a Postgres connection.
  • ADR-0001 still applies. If the venue's internet goes down, the show stops.

Not this weekend

Storybook hosting, preview and staging environments, a separate staging database, error monitoring, presigned uploads with images served from a CDN, and transactional email (#759).
